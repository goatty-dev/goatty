# Plugins (Stage 5)

A goatty plugin packages a command-line tool so that someone who has never used it gets a good setup in one click: goatty downloads the tool into its own directory, shows its most useful options on the **Plugins** settings page with plain-words explanations, and wires those settings into goatty's managed zsh. Nothing outside goatty's directories changes, and nothing runs as root.

Code: `crates/goatty-plugin` (format, trust, bin `goatty-plugin`), `crates/goatty-shell/src/plugins/` (on a host: registries, plans, installs, rendering), `crates/goatty-app/src/settings_window/plugins.rs` (the page). Repositories: [goatty-registry](https://github.com/goatty-dev/goatty-registry) (the official registry) and [goatty-plugin-template](https://github.com/goatty-dev/goatty-plugin-template) (start here to write one; includes a Claude Code skill).

## What a plugin can do

| Mechanism | Manifest | Generated by goatty | Permission |
|---|---|---|---|
| Install programs | `[[package]]` + `[[package.asset]]` (url, sha256, size) | `tools/<pkg>/<version>/`, links in `bin/` (on PATH in goatty shells only) | `binaries` (reason required) |
| Install zsh plugins | `[[package]]` with `source` (a `.zsh` script) and `system_paths` | `plugins/<pkg>` → the package; sourced at the plugin's slot (a distro copy first) | `binaries` (reason required) |
| Load order | `zsh.load` (`line-editor`, `prompt`, `normal`, `last`), `zsh.after` | the plugin's code goes into that slot's file, after the named plugins | – |
| Settings | `[[setting]]` (bool, choice, integer, string, path, list) | controls on the Plugins page, values in `host.json` | – |
| Aliases | `[[alias]]` (command, args templates, `when`) | `alias -- name='cmd args…'`, only when the command exists | `aliases` |
| Environment | `[[env]]` (value template, `when`) | `export NAME='value'` before compinit | `env` |
| Config files | `[[file]]` (`lines` or `text`, optional `env` pointing at it) | a file in the generation, e.g. bat's `BAT_CONFIG_PATH` | `config-files` |
| Completions | `zsh.fpath` (directories in the plugin) | `fpath` entries before compinit | – |
| Shell code | `zsh.init` (a `.zsh` file in the plugin) | sourced at top level with `$goatty_settings` | `shell-code` (reason required) |
| Palette commands | `[[command]]` + `[[command.input]]` (typed inputs: label, placeholder, checks; a list to pick from with `[command.input.source]` + `strict`), `[command.menu]` | an entry in goatty's command palette (and, with `menu`, the terminal's right-click menu) that asks for its inputs, then types its quoted `run` line into the focused terminal | `commands` |
| Snippets | `[[snippet]]` + `[[snippet.input]]` (a command line with `{input}` blanks; typed inputs, flags, several values) | entries in the snippet picker (Ctrl+Shift+S) that ask for their blanks and put the quoted line on the prompt ([`snippets.md`](snippets.md)) | `snippets` |
| Suggestions (lists to pick from) | `[snippet.input.source]`, `[command.input.source]` (`run`: argv of a package executable or required command; `split`, `column`, `label`, `detail`, `skip`, `on_fail`, `timeout`) | the host runs it when the field opens, in the pane's directory, without a shell | `snippet-sources` (reason required) |
| Expansions | `[[expansion]]` (`say` → `to`, placeholders typed `word`/`integer`) | a row in the generation's `expansions.zsh`, rewritten on Space by goatty's widget | `snippets` |
| Needs a system program | `[requires] commands` | integration only when present (`plugin:x missing` otherwise) | – |
| Needs other plugins | `[requires] plugins` | the missing ones are installed along with it, after one review | – |

Everything goatty writes itself is quoted: a setting value can never become shell syntax (`tests: values_cannot_escape_quotes` runs real zsh). The only code a plugin brings is its `zsh.init` file, which is shown in full before installing and re-checked against its approved checksum every time a configuration is built.

Not yet: application plugins (UI, commands that run code inside goatty) need a runtime goatty doesn't have (category `application` is rejected; WASM later, plan §7). Tracked: prompt modules (#96), other shells (#103), macOS and zip/tar.xz (#97), more first-party plugins (#99), index expiry (#100), installing an imported profile's plugins (#101), publishing the repos (#93).

## The manifest (`plugin.toml`)

The template's [`plugin.toml`](https://github.com/goatty-dev/goatty-plugin-template/blob/main/plugin.toml) explains every field in comments. In short:

```toml
schema = 1                      # format version; a newer one is refused ("needs a newer goatty")
id = "eza"                      # [a-z][a-z0-9-]{1,39}
name = "eza"
version = "1.0.0"               # the plugin's semver (bump on any change)
summary = "A modern ls: …"      # one line
description = """…"""           # a few sentences for the details view
publisher = "goatty"
homepage = "https://eza.rocks"
license = "EUPL-1.2"            # the tool's
keywords = ["ls", "files"]
category = "environment"        # or "prompt"

[compat]
goatty = ">=0.0.1"              # semver requirement
os = ["linux"]
shells = ["zsh"]                # default

[requires]
commands = ["docker"]           # must exist on the host; goatty won't install them
plugins = []                    # installed along with it (from the registries) when missing

[[package]]
id = "eza"                      # tools/<id>/
version = "0.23.5"              # the tool's version
bin = ["eza"]                   # relative to the asset root; linked as bin/<name>
prefer_system = true            # default: use a copy already on PATH instead of downloading
completions = ["eza", "--completions", "zsh"]   # optional: prints the zsh completion function;
#                                 the first word is one of `bin`. Runs once after goatty installs
#                                 its copy, kept as `_eza` on fpath (system copies bring their own)

# A zsh plugin instead (or as well): a script goatty sources at the plugin's
# load slot, after zsh.init ran (so init can set the variables it reads).
# source = "zsh-autosuggestions.zsh"     # relative to the asset root; linked as plugins/<id>/
# system_paths = ["/usr/share/zsh/plugins/zsh-autosuggestions/zsh-autosuggestions.zsh"]
#                                       # distro copies, checked first; only under /usr/, /opt/homebrew/,
#                                       # /opt/local/, /run/current-system/sw/, /nix/var/nix/profiles/

[[package.asset]]
target = "x86_64-linux"         # x86_64/aarch64 × linux/macos, or "any"
url = "https://github.com/…/eza_x86_64-unknown-linux-musl.tar.gz"   # https only
sha256 = "e06eeb…"              # checked before anything is unpacked
size = 1412332
format = "tar.gz"               # or "binary" (the download is the executable)
root = ""                       # directory inside the archive

[[setting]]
id = "icons"                    # host.json: plugins.eza.settings.icons
label = "File icons"
help = "A small icon before each name … needs a Nerd Font"
type = "choice"
default = "auto"
arg = "--icons={value}"
group = "Look"                  # heading on the page
advanced = false                # behind "Show advanced settings"
choices = [
  { value = "auto", label = "Automatic", help = "…" },
  { value = "never", label = "Never", arg = "" },   # per-choice arg ("" = none)
]
# integer: min, max, step, unit · string/path/list: placeholder · list: separator · bool: arg, arg_off

[[alias]]
name = "ls"
command = "eza"                 # a package executable or a required command
args = ["{args}"]
when = "replace_ls"

[[env]]
name = "_ZO_EXCLUDE_DIRS"
value = "{exclude}"             # empty → not exported

[[file]]
name = "config"
env = "BAT_CONFIG_PATH"
format = "lines"                # or "text" with template = """…"""
lines = ["{args}"]

[zsh]
init = "zsh/init.zsh"
fpath = ["zsh/completions"]
when = "completion"
load = "normal"                 # line-editor | prompt | normal (default) | last
after = ["fzf"]                 # in the same slot, load after these plugins when they're there

[[command]]                     # an entry in the command palette (#91)
id = "tree"                     # palette id: plugin.eza.tree
title = "Show a folder as a tree"
keywords = ["list"]
run = ["eza", "--tree", "--level={depth}", "{dir}"]   # first word: a package executable or required command

[[command.input]]               # asked in order
id = "dir"
label = "Folder"
type = "folder"                 # text | integer | number | path | folder | choice
default = "."
# placeholder, help, optional, min/max (integer, number), pattern + pattern_help (text),
# choices = [{ value, label, help }] (choice), must_exist (path, folder)

[[command.input]]
id = "file"
label = "File"
strict = true                   # with a source: pick from its list (else a suggestion you can type over)
[command.input.source]          # the list, from a program on the tab's host (same format as a snippet's source)
run = ["eza", "-1", "--only-files", "{dir}"]   # argv, no shell; earlier inputs as arguments

[[snippet]]                     # a command line with blanks for the snippet picker (#89, docs/snippets.md)
id = "tree"
title = "Show a folder as a tree"
line = "eza --tree --level={depth} {dir}"   # shell text; every {input} becomes one quoted word
safety = "safe"                 # safe | changes | destructive (else goatty guesses)
[[snippet.input]]               # the [[command.input]] fields, plus source/strict/multiple, type = "flag" + on
id = "dir"
label = "Folder"
type = "folder"
[snippet.input.source]          # optional suggestions: run on the host (snippet-sources permission)
run = ["eza", "-D", "-1"]

[[expansion]]                   # plain words → a command, on Space
say = "| as tree"
to = "| eza --tree"

[permissions]
binaries = "eza is a program: goatty downloads its official release …"
shell-code = "…"
network = "…"                   # declare when the tool itself uses the network
```

Validation (`goatty_plugin::manifest::parse`) reports every problem with its path (`setting.icons.default: …`). It refuses unknown keys (typos), non-https URLs, malformed checksums, aliases for commands the plugin doesn't provide, environment variables that would change how everything behaves (`PATH`, `LD_*`, `ZDOTDIR`, `GOATTY_*`, …), files outside the plugin directory, symlinks, and files over 1 MiB (4 MiB per plugin).

### Palette commands

A `[[command]]` is an entry in goatty's command palette, shown as "<plugin name>: <title>" (id `plugin.<plugin>.<command>`). Picking it opens its `[[command.input]]`s in the palette one at a time: the label above the field, the placeholder in it, `default` filled in, `help` under it, and the check as you type (`Required`, `Must be a whole number`, `Must be between 1 and 9`, the `pattern_help` for a `pattern` that must match the whole value, `Pick one from the list`). Choices are listed to pick from; a text input with a `[command.input.source]` lists what its program printed (fuzzy search over value, label and detail; with `strict = true` only those are answers, so it's a list to pick from: a container, a branch, a profile); path and folder inputs list the folder being typed when the host is this computer (Tab fills in) and check `must_exist` there. Enter goes on, Esc goes back.

With the answers, goatty types the `run` line into the focused terminal and presses Enter, so the user sees exactly what runs (it's in their history too). Each `run` word is a template with `{input}` (inside a word too: `--level={depth}`); goatty quotes every word for the shell, a whole-word `{input}` whose optional value is empty is left out, and a path or folder value starting with `~/` keeps the `~/` unquoted so the shell expands it (inside a word, `--out={dir}`, it becomes `"$HOME"`). Values can't contain control characters, which would act as keys when typed. A value can't become shell syntax (`commands::tests::quoted_lines_survive_a_real_shell`). Before typing, goatty clears what was typed at the prompt (Ctrl+E Ctrl+U; Ctrl+Y brings it back). When another program runs in the focused pane (or shell integration reports a running command), or the active tab is on another host than the one the command came from, goatty doesn't type and offers to copy the line instead. Relative path answers are checked in the focused pane's directory, where the command runs.

A command can also be in the terminal's right-click menu (#186), under a heading with the plugin's name (more than three plugin entries fold into a "Plugins" submenu):

```toml
[command.menu]
icon = "search"        # one of goatty_plugin::commands::MENU_ICONS; default: the plugin icon
when = "selection"     # always (default) | selection (text is selected) | prompt (a shell waits)
fill = "container"     # when = "selection": the text or path input the selected text fills in
```

The selected text (its first non-empty line, without control characters) only fills in the input's starting value: the inputs are still asked, so the user sees and can change it before anything is typed. The install plan lists such commands with "(also in the right-click menu)". `menu` is only serialized when present, but a goatty older than this one refuses manifests that use it, so set `compat.goatty` accordingly.

The commands come from the plugins installed and enabled on the active tab's host, so a remote host's plugins bring their commands while a tab on it is active. Validation checks ids, that `run`'s first word is one of the plugin's executables or required commands (no template), that every `{x}` is an input, and each input's type-specific fields (`min` ≤ `max`, a valid `pattern`, `choices` only and always for `choice`, `default` passing the input's own check), for a `[command.input.source]` the same rules as a snippet's (the host runs it from its own copy of the manifest, `Request::CommandSuggest`; a goatty older than this one refuses manifests with `source` or `strict` on a command input, so set `compat.goatty` accordingly) (a `run` whose first word is one of the plugin's executables or required commands, no `sh`, only earlier inputs as `{x}`, only on text inputs; `strict` only with a source), and for `[command.menu]` the icon name and that `fill` is a text, path or folder input of a `when = "selection"` command.

### Templates

Used in alias `args`, `[[env]] value`, `[[file]] lines`/`template`:

| | Meaning |
|---|---|
| `{id}` | the value: strings as they are, bools `true`/`false`, lists joined with `separator` (default space) |
| `{id.arg}` | the setting's command-line argument(s): bool `arg` when on (`arg_off` when off); choice: the choice's `arg` or the setting's; lists: one per entry; nothing for empty values |
| `{args}` | every setting's arguments, in manifest order |
| `{value}` | inside a setting's own `arg` |
| `{{`, `}}` | literal braces |

As a whole list item, `{id.arg}`/`{args}` expand to zero or more items. Inside a string they're joined with spaces, each quoted for a POSIX shell where needed (for variables holding a command, like `FZF_DEFAULT_COMMAND`). `~` and `~/…` in path settings and list entries become the home directory.

Conditions (`when`): `id` (bool on), `!id`, `id=value`, `id!=value`; checked against the settings at validation.

### Settings at runtime

Stored values live in `host.json` under `plugins.<id>.settings` (an open map, so `goattyd settings set plugins.eza.settings.icons always` works too). When a configuration is built, each value is checked against the plugin's schema: a bad one falls back to the default and is reported (`plugins.eza.settings.git: expected a bool, got "yes"; using the default`), the others are kept, like every other setting. `plugins.<id>.enabled = false` keeps a plugin installed but out of the shell.

While a plugin's `zsh.init` runs, `$goatty_settings[<id>]` holds each value (lists joined with spaces) and `$goatty_plugin_dir` its directory in the generation; both are unset afterwards.

### Load order

Where a plugin's aliases, init code and package scripts go in the managed `.zshrc` (its environment and `fpath` always go into `plugins-early.zsh`, before `compinit`):

| `zsh.load` | File | Position | For |
|---|---|---|---|
| `line-editor` | `plugins-line-editor.zsh` | after `compinit`, before the prompt | tools that add widgets and key bindings: fzf, fzf-tab, autosuggestions |
| `prompt` | `plugins-prompt.zsh` | the prompt; goatty sets a small one when no prompt plugin loaded | Starship |
| `normal` (default) | `plugins.zsh` | after the prompt, before the user's aliases, integration and additions | most plugins |
| `last` | `plugins-last.zsh` | after `~/.config/goatty/zshrc` | what must wrap every widget defined before it: syntax highlighting |

Within a slot, a plugin loads after the ones its `zsh.after` names (when they're installed and on), otherwise built-in plugins first, then by id (`goatty_shell::plugins::load_order`; a cycle is broken, never hangs). An `after` naming a plugin in an earlier slot is always satisfied. In the generated block, the init code runs first, then each package's `source` script (found as `$_goatty_src[<pkg>]`), then the status is recorded.

## Permissions

`snippets` (snippets and expansions) needs no reason either: nothing runs, a snippet's line is put on the prompt for the user to read and run, and an expansion is shown before it runs (Backspace undoes it); the plan lists every line and rewrite. `snippet-sources` (snippet and command suggestions) needs a reason: it runs the listed programs with the listed arguments when a field opens (on the tab's host, in the pane's directory, without a shell, stopped after a few seconds), and the plan lists each one. Plugins can't use a shell pipeline as a source (`sh`, only for the user's own snippets).

`commands` (palette commands) needs no reason: nothing runs until the user picks the command and fills in its inputs, and what runs is typed into their terminal. The plan lists each command with its `run` line.

goatty doesn't take a plugin's word for what it does. Permissions are derived from the manifest's contents (`goatty_plugin::permissions::derived`): a `[[package]]` *is* the `binaries` permission. The author must explain the powerful ones (`binaries`, `shell-code`, `network`) in `[permissions]`; using one without a reason, or declaring one the manifest doesn't use, fails validation. The install plan lists each permission with its meaning, the author's reason and the concrete details (programs, alias names, variable names, files).

`binaries` and `shell-code` run code with the user's privileges. A registry signature proves where a plugin came from and that it wasn't changed; it doesn't make a program harmless. That's what the registry review ([REVIEW.md](https://github.com/goatty-dev/goatty-registry/blob/main/REVIEW.md)) and the approval step are for.

## Registries and trust

A registry is a Git repository:

```
registry.toml               name, trusted public keys (Ed25519, hex), yanked "id@version"s
plugins/<id>/<version>/     plugin directories; published versions are never edited
index.json                  every plugin version with the sha256 of each of its files, a sequence number
index.json.sig              {"key", "signature"} over the exact bytes of index.json
```

The chain of trust:

1. goatty pins the official registry's key (`goatty_shell::plugins::registry::OFFICIAL_KEYS`). Other registries are added with their key explicitly (`goattyd plugin registry add NAME URL --key HEX`); there's no trust on first use.
2. Refreshing downloads the registry (a `.tar.gz` of the repository, by default GitHub's archive of `main`; or an absolute directory) into a temp dir, then checks the signature by a trusted key, the format, the `sequence` (lower than the stored snapshot's → refused, so an old index can't be replayed), and the sha256 of every listed file. Only then are exactly the listed files copied into `~/.local/share/goatty/registries/<name>/`. On any failure the old snapshot stays.
3. The index pins every plugin file; the manifest pins every download.
4. A plan carries a digest over everything security-relevant (id, version, source, every file's checksum, every download URL + checksum, whether a system copy is used, permissions, the shell code, and the digests of the plans of the plugins it needs that come along). Installing sends the digest back; goatty recomputes the plan and refuses if it differs ("changed since you reviewed it"). What gets installed is exactly what was approved.
5. Installed files are kept with their checksums in `installed/lock.json`. Each configuration build checks the files it sources again; a changed file takes the plugin out with an issue instead of sourcing it.

Signing happens offline: the maintainer runs `scripts/publish.sh <secret key>` (validate, re-download every asset, `index build`, `index sign`, `index verify`) and commits the index. The registry's CI verifies the signature against the pinned key, validates every plugin and checks every download, but never holds the key. Contributors' pull requests only add plugin directories. Key rotation: add the new key to `registry.toml` and `OFFICIAL_KEYS`, release, sign with the new key, later drop the old one.

`registries.json` (`$XDG_CONFIG_HOME/goatty/`) holds added registries; `"builtin": false` turns the official one off (an organization that only allows its own registry, or tests).

## On a host

```
~/.local/share/goatty/
  registries/<name>/          verified registry snapshots (.fetched: when)
  installed/<id>/             verified copy of each installed plugin's files
  installed/lock.json         version, source, file checksums, packages, permissions, approved digest
  tools/<pkg>/<version>/      unpacked packages (built-in and installed plugins')
  bin/<exe>                   → tools/…; a link owned by another package or a user file is never replaced
  plugins/<pkg>               → tools/<pkg>/<version>/<root>, for packages with a `source` script
  share/zsh/site-functions/   `_<exe>` from a package's `completions` command (and goatty's own), on fpath
  current/zsh/
    plugins-early.zsh         fpath + exports (sourced before compinit), `off` for turned-off built-in plugins
    plugins-<slot>.zsh        aliases + init code + package scripts, per plugin guarded by
                              `(( $+commands[...] && ${+_goatty_src[...]} ))`; plugins.zsh is the normal slot
    plugins/<id>/…            generated config files and the plugin's shell files
```

Load order in the managed `.zshrc`: options, history, PATH, **plugins-early.zsh**, keys, compinit, (user .zshrc), **plugins-line-editor.zsh**, **plugins-prompt.zsh** (or the fallback prompt), **plugins.zsh**, the user's aliases, integration, the user's `~/.config/goatty/zshrc` (so the user can override a plugin's alias), **plugins-last.zsh**. `goatty-status` reports each installed plugin as `plugin:<id>` and each built-in one as `<id>` (ok with the command's or script's path, `missing`, or `off`); `goatty-setup` and the missing-tools hint only concern the built-in plugins marked for default install.

Install (`HostService::install_plugin`): lock `installed/.lock` → recompute the plan and compare the digest → download every package not already on PATH (kept on disk under `installed/` until activation, removed afterwards) → stage the plugin's files (verified) → *activate*: verify and unpack each package to a staging dir, link → swap in the plugin's files → update the lock → enable it in `host.json` and build a validated generation (`zsh -n` on every `.zsh`, including the plugin's) → offer to reload running shells. A failure undoes the packages this attempt added. Updating is the same with a newer version: packages the new version dropped are removed.

Required plugins (`[requires] plugins`, #94): the plan resolves the ones that aren't installed (or built in), and what those need, from the registries (newest version; a cycle or a plugin no registry has fails the plan) and includes each one's own plan in `Plan::dependencies`, in install order. The one approval covers them all: their digests are part of the plugin's. Installing downloads and stages every plugin of the install before activating any (a cancel still leaves the host as it was), then activates them dependencies first and enables each in `host.json`. Their lock entries say `"dependency": true`. Uninstalling a plugin returns (`Changed::unneeded`) the plugins installed as dependencies that nothing installed needs any more, in an order they can be removed in; the CLI asks whether to remove them too (`--yes` without asking), the settings window offers it in a toast. A plugin installed on its own is never offered, and a dependency that's turned off is a warning in the plans of plugins that need it.

Each install is a job (`plugins::jobs`, #102), shared by all of goattyd's connections: `installs` reports it (waiting for another plugin change, downloading package N of M with bytes so far, activating) and `cancel_install` stops it while it waits (also while another install holds the lock) or downloads. Nothing on the host changes before activation, so a cancel leaves it exactly as it was; once activating, a cancel is refused. A finished install's outcome (done with its `Changed`, failed, cancelled) stays listed for 15 minutes, so a client whose connection dropped mid-install learns how it ended after reconnecting. The same plugin can't be installed twice at once.

Updates (#95): goattyd fetches registries older than a day in the background (two minutes after start, then hourly checks), only while a plugin from a registry is installed. `updates` lists installed plugins with a newer version in their registry, with the permissions the new version adds. Nothing is ever installed this way: an update goes through the same plan and approval as an install. Uninstall removes packages (unless another plugin needs the plugin), files, the lock entry and the `host.json` entry, then rebuilds.

Conflicts are refused at plan time: a plugin id, package id or executable of a built-in plugin (`starship`, `fzf`, `fzf-tab`, …), another plugin's executable, or a file in `bin/` goatty didn't create. Alias names shared with another plugin or an existing command are warnings in the plan.

## Built-in plugins

fzf, fzf-tab, autosuggestions, syntax-highlighting, starship and basics (snippets and expansions only, nothing to install; [`snippets.md`](snippets.md)) come with goatty (`crates/goatty-shell/plugins/<id>/`, compiled in by `goatty_shell::builtins`; table with pins and slots in [`managed-zsh.md`](managed-zsh.md#installing-and-updating-tools)). They're ordinary manifests (validated by the same parser, `builtins::tests`), so they get install plans, settings on the Plugins page and load-order slots. The differences:

- **Always there.** No lock entry and no copy in `installed/`: their files are part of goatty, read from the binary when a generation is built. They're on unless `plugins.<id>.enabled` is `false`; `goattyd plugin disable fzf-tab` (or the switch on the Shell/Prompt/History page) turns one off, and `goatty-status` says `off`. Uninstalling is refused; `goattyd shell uninstall <id>` removes goatty's download of the tool.
- **Planning one = its packages.** `find("fzf")` always resolves to the built-in plugin (a registry can't shadow it). Its plan lists each package as already on the system, already installed by goatty at the pinned version (`current`), or to download; installing downloads only the latter. `goattyd shell install` and `goatty-setup` use exactly this.
- **Works with system copies anywhere.** Only a download needs a build for the host, so on macOS a Homebrew Starship is used even though goatty has no managed build there (#97).
- **Updates come with goatty releases**, like the pins did. After a pin bump, `goattyd shell status`, `goattyd shell update`, `goatty-setup`, the in-shell hint, Diagnostics, `goattyd plugin list` and the Plugins page all flag older managed copies and offer to update them (#45).
- Their packages keep the ids of the old tool table, so installs made before #98 are found where they are. Their init code may use goatty's own variables (`$_goatty_dir` for the generated `starship.toml`); registry plugins shouldn't.

## Using it

**GUI:** Settings → **Plugins** (`Ctrl+,`, or the palette: "Plugins: browse, install and configure"). Installed plugins show their settings as controls (toggles, segmented choices or a list for more than four, steppers, text fields), grouped, with help text; edits go into the same host draft as the Shell page (Preview/Apply). Available plugins show permission badges; **Review & install…** shows the plan (downloads with checksums, permissions with reasons, aliases, environment, "Read the code" for shell code, warnings; the same for each plugin it needs that comes along) with **Install**/**Cancel**. Uninstall asks twice, then offers to remove the plugins only it needed. While an install runs, the page shows its progress (package N of M, bytes) with **Cancel** until it's activated; if the connection drops, the page keeps following the install on the host and reports its outcome once the connection is back (or when the Plugins page is opened again while it still runs). When the active tab's host has plugin updates, a toast says so ("2 plugin updates", **Review** opens the installed list); the host is asked when the active host changes and at most every 6 hours, each update is told once per app run, and `plugins.notify_updates` (client setting, **Tell me about plugin updates** on the Plugins page) turns it off. With a remote goattyd all of this happens on that host.

**CLI** (`goattyd plugin …`, on the host):

```
search [QUERY] [--refresh]        what the registries offer
info ID                           details, settings with help, permissions
install ID[@VERSION]… [--yes]     print the plan, ask [y/N] (no terminal: needs --yes)
install --path DIR                a local plugin (marked "local, unverified")
update [ID…] [--yes]              newer versions, same review
uninstall ID… [--yes]             --yes: also the plugins only they needed, without asking
list                              installed, enabled, updates, problems
enable|disable ID
set ID KEY VALUE | unset ID KEY   checked against the plugin's schema
registry list|refresh|add NAME URL --key HEX|remove NAME
```

**Authors** (`goatty-plugin`, `cargo install --git https://github.com/goatty-dev/goatty --locked goatty-plugin`): `new ID`, `validate [DIR]`, `render [DIR] --set k=v`, `hash URL|FILE…` (sha256, size, executables in the archive), `check-downloads [DIR…]`; maintainers: `index build|sign --key|verify [--trust HEX]|check`, `keygen FILE`.

## Protocol (v5)

`ClientMsg::Plugin { req, request }` → `ServerMsg::Plugin { req, reply }`, both JSON (`goatty_plugin::api::{Request, Reply}`: `catalog`, `plan`, `install` with the approved digest, `uninstall`, `snippets`, `suggest`, `installs`, `cancel_install`, `updates` → `Catalog`, `Plan`, `Changed`, `Snippets`, `Suggestions`, `Installs`, `Updates`). goattyd answers on a separate thread (installs download; the connection's input must not wait), and the client waits up to 10 minutes for the reply; progress comes from polling `installs` on the same connection. New operations or fields don't need a protocol bump. Plugin settings travel with the host settings (`SetHostSettings`).
